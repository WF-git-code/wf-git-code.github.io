关键 API 说明（C++ 专属）

  1. SerializeToString(string*) 对象转二进制字符串
  2. ParseFromString(const string&) 二进制解析对象
  3. SerializeToOstream 直接写入文件流
  4. ParseFromIstream 从文件流读取
  5. mutable_xxx() 获取可修改指针（嵌套 /map/repeated）
  6. has_xxx() proto2 支持；proto3 零值不传输，无 has 接口

四、Protobuf (C++) VS JSON 对比

维度 JSON（nlohmann/json rapidjson） Protobuf C++
数据格式 明文文本 紧凑二进制
包体积 大，key 重复、符号冗余 小 30%~80%，只用数字编号
CPU 性能 字符串分词、转义开销大 二进制偏移读取，性能提升数倍
类型安全 弱类型，数字 / 字符串易错乱 编译期强类型校验
版本兼容 增减字段极易解析异常 天然前后兼容
调试 直接打印查看 必须代码解码才能打印内容
C++ 依赖 第三方库 protobuf 官方库，RPC 场景原生适配
对外接口 前端 / 第三方通用 仅内网服务使用

五、C++ 项目适用场景

推荐 Protobuf

  1. C++ gRPC /brpc 微服务内网通信
  2. C++ Kafka/RocketMQ 海量日志、事件消息
  3. 高性能网关、存储服务、底层中间件
  4. 跨语言服务（C++ <-> Java/Go/Python）
  5. 本地磁盘持久化缓存、二进制落盘

推荐 JSON

  1. HTTP 对外接口、与前端交互
  2. 需要动态不定字段配置
  3. 频繁在线打印原始报文调试

六、版本兼容 & C++ 工程容灾设计（核心）

1. Schema 兼容规范（防止宕机解析崩溃）

  1. 字段编号永不复用

    删除字段必须加

    ，新旧 C++ 程序并行灰度不报错。

  2. 只新增字段，禁止修改原有字段类型

    int64 不能改成 string，二进制解析乱码。

  3. 枚举只能追加，不能删除原有枚举值。

  4. 灰度发布顺序：先部署消费端（解析方），再部署生产端。

3. MQ 传输容灾（C++ MQ 客户端）

  1. 消息 Header 增加标识

    区分 JSON/PB 二进制，防止混传解析崩溃。

  2. 单条消息限制最大长度，避免超大 PB 报文内存 OOM。

  3. MQ 持久化 + 本地文件双备份，磁盘二进制损坏可重放 MQ 恢复。

4. 内存脏页宕机场景配套

PB 仅负责序列化，数据持久化可靠性依靠：

  • 磁盘 write+fsync 刷盘；

  • MQ 同步落盘；

  • 数据库 redo 日志兜底；

    PB 本身不提供持久化保障，只解决二进制编解码。

八、C++ 高频踩坑与最佳实践

  1. proto3 零值不序列化

    id=0、空字符串不会写入二进制，C++ 读取默认 0，无法区分 “未传” 和 “值为 0”；业务增加标记字段判断。

  2. 超大 repeated 数组导致内存暴涨

    C++ 堆内存分配过大触发 OOM，限制单条消息大小。

  3. 嵌套层级过深栈溢出

    message 嵌套控制在 10 层以内。

  4. 忘记链接 protobuf 库，编译报未定义引用。

  5. 二进制跨语言传输时字节序无需处理，Protobuf 内部统一编码。
