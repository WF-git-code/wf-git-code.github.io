1. 设计哲学与核心思想

muduo 是陈硕开发的基于 Reactor 模式的 C++ 网络库，其设计根植于现代 Linux 多线程服务端编程的最佳实践。

核心信条：

  • One loop per thread：每个线程最多有一个 EventLoop，EventLoop 是线程的唯一主人。
  • 非阻塞 IO + LT（水平触发） epoll：采用非阻塞 IO，与 epoll LT 模式结合，编程更简单，不易漏事件。
  • RAII 与智能指针管理对象生命周期：通过 shared_ptr 和 weak_ptr 避免悬垂指针，尤其是在多线程回调中。
  • 事件驱动与回调机制：所有 IO 事件、定时器事件、跨线程调用都通过回调完成，用户只需设置回调即可。
  • 线程安全由 EventLoop 保证：对某个 TCP 连接的读写操作都在其所属 IO 线程进行，无需额外加锁。
  • 库的边界清晰：网络库只管网络，不侵入业务逻辑，不强制线程池与业务线程模型。

2. 总体架构

muduo 的主要类及其关系可概括为：

text

组件交互流程：

  1. 用户创建 TcpServer，设置回调（连接建立、消息到达、消息发送完成、连接关闭）。
  2. TcpServer 启动监听，将 Acceptor 的 Channel 注册到主 EventLoop 中。
  3. 新连接到来，Acceptor 接受连接，轮询选择一个子 EventLoop，创建 TcpConnection 对象并分发过去。
  4. TcpConnection 将自身的 socket Channel 注册到子 EventLoop 中，开始监听读写事件。
  5. 数据到达时，Poller 返回就绪事件，EventLoop 调用对应 Channel 的回调，最终触发 TcpConnection::handleRead，读取数据并调用用户的 messageCallback。
  6. 用户可主动调用 TcpConnection::send 发送数据，若无法一次性发送完毕，则注册写事件，等待可写时继续发送（由 Buffer 输出缓冲区管理）。

3. 核心组件详解

Channel

定位：负责将一个文件描述符（fd）及其关心的事件（读、写、错误等）与相应的回调函数绑定，并注册到 EventLoop 的 Poller 中。它是 Reactor 模式中“事件处理器”的抽象。

关键成员：

  • int fd_：监听的描述符。
  • int events_：用户关心的事件（EPOLLIN/EPOLLOUT 等）。
  • int revents_：Poller 返回的就绪事件。
  • EventLoop* loop_：所属的 EventLoop。
  • 回调函数：readCallback_、writeCallback_、closeCallback_、errorCallback_。
  • int index_：用于 Poller 快速判断 Channel 是否已在 epoll 监听队列中（-1 未添加，1 已添加，2 已添加但后来被删除）。

职责：

  • enableReading() / enableWriting()：更新关心的事件，并调用 EventLoop::updateChannel 使 epoll 监听生效。
  • handleEvent(Timestamp receiveTime)：根据 revents_ 分派到具体的回调。
  • remove()：从 EventLoop 中移除自身，与 fd 解绑。

设计要点：

  • Channel 并不拥有 fd，它只是一个包装器，fd 的真正关闭由 Socket 或 TcpConnection 负责。
  • 一个 fd 只能对应一个 Channel，Channel 也不能跨 EventLoop 使用。

Poller / EPollPoller

定位：封装 IO 多路复用系统调用（epoll_wait），EventLoop 通过 Poller 获取就绪事件列表。

核心接口：

  • Timestamp poll(int timeoutMs, ChannelList* activeChannels)：执行 epoll_wait，将就绪的 Channel 填入 activeChannels。
  • void updateChannel(Channel* channel)：添加或更新 Channel 在 epoll 中的监听事件。
  • void removeChannel(Channel* channel)：从 epoll 中移除 Channel。

实现细节：

  • EPollPoller 使用 epoll_create1(EPOLL_CLOEXEC) 创建 epoll 实例。
  • 内部维护 std::map<int, Channel*> channels_，以 fd 为键快速查找 Channel，便于 updateChannel 时判断是新增（EPOLL_CTL_ADD）还是修改（EPOLL_CTL_MOD）。
  • 使用 LT 模式，无需担心事件丢失，但需要自行处理事件循环的效率和缓冲区大小。

EventLoop

定位：事件循环的核心，整个 muduo 的“发动机”。每个线程至多拥有一个 EventLoop。

关键功能：

  1. 循环驱动：loop() 函数不断调用 poller_->poll 获取活跃 Channel，然后执行其回调。
  2. 跨线程任务调度：runInLoop(Functor) 和 queueInLoop(Functor) 可将任务安全地放入特定 IO 线程执行，避免锁竞争。
  3. 定时器集成：持有 TimerQueue，支持 runAt、runAfter、runEvery 等方法。
  4. 生命周期管理：通过 eventfd 实现唤醒机制，当其他线程向当前 EventLoop 投递任务时，需要唤醒 epoll_wait。

关键成员：

  • std::unique_ptr<Poller> poller_：实际 poll 实现。
  • std::unique_ptr<TimerQueue> timerQueue_：定时器队列。
  • int wakeupFd_：eventfd 创建的描述符，用于线程唤醒。
  • std::unique_ptr<Channel> wakeupChannel_：监视 wakeupFd_ 的 Channel。
  • bool looping_、bool quit_：控制循环状态。
  • MutexLock mutex_ 和 std::vector<Functor> pendingFunctors_：线程安全的待执行回调队列。
  • const pid_t threadId_：记录 EventLoop 所属线程 ID，用于断言检查。

跨线程执行保证：

  • 如果调用者就是 EventLoop 所属线程，则直接执行回调。
  • 否则，将回调加入 pendingFunctors_ 队列，并 wakeup() 唤醒 epoll_wait。唤醒后，在 doPendingFunctors 中取出并执行。

TimerQueue

定位：基于 timerfd 和 std::set 实现的定时器管理，将所有定时器集成到 EventLoop 的 IO 复用中。

设计：

  • 使用 timerfd_create 获取一个定时器专用 fd，通过 timerfd_settime 设置超时时间。
  • 当 timerfd 可读时，说明有定时器到期，TimerQueue 处理到期事件并调用用户的 TimerCallback。
  • 内部用 std::set<std::pair<Timestamp, Timer*>> 按到期时间排序，每次取出最早到期的一批定时器。
  • 支持一次性定时器 runAt/runAfter 和重复定时器 runEvery，重复定时器在处理后重新计算时间并插入集合。

优点：

  • 将定时器事件与 IO 事件统一，完全由同一个 EventLoop 线程处理，无需额外线程。
  • 精度由内核 timerfd 保证，没有传统定时器的轮询开销。

TcpConnection

定位：代表一个已建立的 TCP 连接，是用户使用最多的接口类。管理连接上的数据收发、缓冲区、状态、生命周期。

重要成员：

  • EventLoop* loop_：所属 IO 线程。
  • std::unique_ptr<Socket> socket_：包装 socket fd。
  • std::unique_ptr<Channel> channel_：注册到 loop 的 Channel。
  • Buffer inputBuffer_：应用层输入缓冲区。
  • Buffer outputBuffer_：应用层输出缓冲区。
  • State state_：连接状态（kConnecting, kConnected, kDisconnecting, kDisconnected）。
  • 回调：connectionCallback_、messageCallback_、writeCompleteCallback_、closeCallback_ 等。
  • std::any context_：用户可绑定任意上下文数据（如每个连接的业务对象）。

核心流程：

  1. 建立连接：构造函数中创建 Socket 和 Channel，设置回调，但 Channel 尚未注册到 Loop。由 TcpServer 调用 connectEstablished() 时，开启读监听，并调用 connectionCallback_ 通知用户。
  2. 读取数据：handleRead() -> socket_.readv 到 inputBuffer_，然后触发 messageCallback_，传递 Buffer* buf 和 Timestamp。
  3. 发送数据：send(const StringPiece&) 将数据追加到 outputBuffer_，若直接 write 未完全发送，则注册写事件，由 handleWrite() 继续发送剩余部分。所有发送完毕后，可触发 writeCompleteCallback_。
  4. 关闭连接：被动关闭时（read 返回 0），调用 handleClose()，改变状态，最终调用 closeCallback_ 通知 TcpServer 移除连接。主动关闭通过 shutdown() 实现半关闭，通过 forceClose() 直接关闭。

生命周期管理：

  • 使用 shared_ptr 管理 TcpConnection，用户、Server、Channel 回调都可能持有。只有所有引用释放后，连接才真正析构。
  • Channel 的回调中若需要延长对象生命，可 shared_from_this() 保护。

TcpServer

定位：用于创建和管理监听套接字以及接受新连接，并分发给多个 IO 线程。

主要组件：

  • Acceptor：封装监听 socket 和 accept，运行在主 Loop。
  • EventLoop* loop_：主 Loop（acceptor loop）。
  • EventLoopThreadPool：工作线程池，每个线程内有一个 EventLoop，通过 round-robin 分配连接。
  • ConnectionMap connections_：保存所有活跃的 TcpConnection 的 shared_ptr，用于管理生命周期、方便外部主动访问。

工作流程：

  1. 用户调用 start()，主 Loop 线程中 Acceptor::listen() 将监听套接字注册到 epoll。
  2. 新连接到达，Acceptor::handleRead() 获得 connfd，从线程池获取下一个 Loop，创建 TcpConnection 对象，然后调用 newConnection 将该连接“安家”到对应 Loop。
  3. TcpServer 持有 connections_ 防止连接过早销毁；当连接断开时，通过 removeConnection 把连接移除。

关键特性：

  • 线程安全：对所有连接的访问必须通过 IO 线程或加锁保护。TcpServer 的 getLoop() 等接口设计清晰。
  • 可设置线程初始化回调：setThreadInitCallback，用于工作线程内部的资源初始化（如登录日志、数据库连接）。

Buffer

muduo 的 Buffer 是模仿 muduo 库中 Buffer 设计的网络应用层缓冲区，非阻塞 IO 必备。

设计特点：

  • 底层是一块连续内存（std::vector<char>），采用分散-聚集读写。

  • 使用读写下标维护数据区域：

    text

  • prependable 空间使得在数据前添加包头变得极其高效（无需移动数据），只需预留 8 字节（通常用于长度字段）。

  • 自动增长策略：当写空间不足时，先尝试将已读空间回收（挪动数据到头部），若仍不足再 resize 扩大。

核心接口：

  • readFd(int fd, int* savedErrno)：使用 readv 配合栈上额外缓冲区，尽可能一次性读走所有数据，减少系统调用。
  • retrieve(size_t len)：移动 readerIndex_，丢弃已读数据。
  • retrieveAllAsString()：取出所有数据作为 string。
  • peek() / peekInt8/16/32/64：查看可读数据而不取走。
  • append(const StringPiece& str)：追加数据到写区域。
  • prepend(const void* data, size_t len)：在前面插入数据（通常用于封包时加长度头）。
  • ensureWritableBytes(size_t len)：确保可写空间足够。
  • swap(Buffer& rhs)：高效交换两个 Buffer 的内容。

零拷贝与高性能：

  • readFd 使用 readv 和栈空间，避免一次 read 不够又需要再次读取的系统调用。
  • 与 TcpConnection 的输出缓冲区配合，发送时通过 writev 结合 header 和 buffer 内容，减少拷贝。

4. 线程模型与并发模型

muduo 采用 主从 Reactor + 线程池 模式：

  • 主 Reactor 线程：仅负责监听新的连接，建立连接后立即分发给工作线程。主 Reactor 通常只有一个。
  • 工作 Reactor 线程：由 EventLoopThreadPool 管理，数量可配置。每个线程独立运行自己的 EventLoop，负责处理分配的连接的所有 IO 事件和定时器任务。

One loop per thread 的好处：

  • 同一连接的所有 IO 都在一个线程内，无需为连接内数据竞争加锁。
  • 用户编写的 messageCallback 总是在固定的 IO 线程调用，可安全访问该线程内部资源。
  • 代码逻辑清晰，避免复杂的线程同步问题。

线程间通信：

  • 通过 EventLoop::runInLoop 或 queueInLoop 将任务推送到目标 IO 线程执行。典型场景：A 线程需要向某个连接发送数据，但不拥有该连接的 Loop，则通过 conn->getLoop()->runInLoop 安全调用 conn->send。
  • EventLoop 内部使用 eventfd 实现异步唤醒。当其他线程向 pendingFunctors_ 添加任务时，写入 wakeupFd_ 以唤醒可能阻塞在 epoll_wait 的 Loop。

互斥锁使用：

  • 每个 EventLoop 有自己的 mutex_ 保护 pendingFunctors_，避免多个线程同时添加任务产生竞争。
  • TcpServer 的 connections_ 容器只在主线程修改（插入/删除），但读取可能在其他线程，因此需要原子操作或通过 Loop 安全调度。

7. 性能优化设计

  • LT 模式 + 非阻塞 IO：避免边沿触发带来的饥饿和编程复杂度，配合合理的 Buffer 可以高效处理数据流。
  • 一次性读取：Buffer::readFd 使用 readv 结合栈上 65536 字节额外空间，尽量一次将 socket 接收缓冲区读空，减少 epoll 触发次数。
  • 发送时 writev：如果输出缓冲非空，sendInLoop 会尝试使用 writev 将主数据头与 Buffer 内容聚集写出，减少系统调用次数。
  • 零拷贝与对象复用：使用 std::vector<char> 作为存储，配合 swap 可以高效地移交数据。TcpConnection 中的 context_ 类型为 std::any，方便绑定各种用户数据。
  • 减少锁竞争：
    • EventLoop 的 doPendingFunctors 使用了 swap 技巧：在锁内将任务队列交换到局部变量，然后释放锁再逐一执行，大大减小临界区。
    • 连接的生命周期管理通过 shared_ptr 和 weak_ptr，在回调中安全地延长对象生命，而不是用互斥锁防止销毁。
  • 线程本地存储：EventLoop 通过 thread_local 或 __thread 保存本线程的 Loop 指针，方便在任何地方通过 CurrentThread::loop() 获取。

8. 常见坑点与避坑指南

  1. 线程安全误区
    • 错误示例：在工作线程外直接调用 conn->send，如果当前线程不是该连接的 IO 线程，可能导致数据竞争。
    • 正确做法：始终通过 conn->getLoop()->runInLoop() 将发送任务交给正确线程，或使用 conn->send 本身在内部判断线程（muduo 的 send 实际上已经做了这个判断，如果不在自己的 loop 中则转发，开发者不必担心，但理解原理很重要）。
  2. 回调中的生命周期管理
    • 问题：在 messageCallback 中直接 conn->forceClose()，可能会让 TcpConnection 对象在本次回调中析构，如果后续代码还使用 conn 则发生未定义行为。
    • 解决：muduo 使用 shared_ptr 管理连接，回调中常通过 shared_from_this() 延长生命。如果确实需要断开，应借助 queueInLoop 延迟关闭，或让库本身的 forceClose 实现保障安全。实际上 muduo 的 handleClose 会在当前事件处理完后才移除连接，并保证多次调用安全。
  3. Buffer 粘包与拆包
    • muduo 只提供字节流，用户必须自己处理消息边界。常见方法：定长、分隔符、长度前缀。如果没处理好，messageCallback 可能收到不完整包，导致业务逻辑错误。建议在 onMessage 中使用 while 循环提取完整包，未完整的数据保留在 Buffer 中，待下次数据到达再处理。
  4. 阻塞 EventLoop
    • 在 IO 线程的回调（如 messageCallback、connectionCallback、定时器回调）中执行耗时操作（计算密集、同步磁盘 IO 等）会阻塞整个 Loop，导致该线程的其他连接无法及时响应。解决方案：将耗时任务交给独立工作线程池，通过回调返回结果。
  5. 连接对象泄漏
    • 如果用户没有正确管理 TcpConnection 的 shared_ptr，或者 closeCallback 未将连接从 Server 的 connections_ 中移除（但 muduo 已经自动处理），可能导致连接泄漏。开发人员需注意不要在回调外长期持有 TcpConnectionPtr 导致连接无法正常关闭。
  6. 多线程操作同一连接
    • 原则上不允许两个线程同时操作一个 TcpConnection，虽然 send 内部保证线程安全，但业务侧访问 context_ 时若没有同步则会出现数据竞争。确保业务数据只在连接所在的 IO 线程访问。
  7. 高水位回调与内存控制
    • 如果对端接收慢而本端发送快，outputBuffer_ 可能堆积大量数据，占用内存。应设置 HighWaterMarkCallback 来暂停发送或应用限流，否则可能导致服务器 OOM。
  8. 定时器失效问题
    • 定时器回调中如果捕获了 shared_ptr<TcpConnection>，可能导致连接无法释放。定时器应在连接断开时及时取消：muduo 的 TimerQueue 持有 TimerId，可以调用 loop->cancel(timerId)。通常将定时器 ID 保存在连接上下文，在连接关闭回调中取消。
  9. eventfd 唤醒的惊群？
    • 每个 EventLoop 有自己的 wakeupFd_，不存在多个 Loop 共享一个 eventfd 的情况，所以没有惊群问题。
  10. 代码中使用 boost 依赖
    • muduo 重度依赖 boost（function、bind、shared_ptr、any 等），C++11 时代可以使用标准库替代，但源码依然依赖 boost。若项目不能引入 boost，需自行改造。
