一、Docker 是什么？为什么需要它？

想象一下，我们把开发好的应用程序及其所有依赖（比如代码、运行时、系统工具、库）全部打包到一个“集装箱”里。这个集装箱是标准化的，可以在任何支持 Docker 的机器上运行，无论这台机器是 Windows、macOS 还是 Linux，也无论它是什么版本。

这个“集装箱”，就是 Docker 容器 (Container)。

Docker 的核心价值：

环境隔离与一致性： 确保开发、测试、生产环境完全一致，告别环境问题。

快速部署与启动： 容器是秒级启动，远快于传统的虚拟机。

资源利用率高： Docker 容器直接运行在宿主机内核上，几乎没有性能损耗。一台物理机可以运行成百上千个容器。

简化运维： 便于迁移、扩展和管理。

DockerVS虚拟机

对比项 虚拟机 (VMware/VirtualBox) Docker 容器
内核 独立完整操作系统内核，占用极高资源 共享宿主机内核，仅打包应用 + 依赖
启动速度 分钟级 秒级启动
资源占用 每台虚拟机分配独立内存 CPU 轻量，可同时跑上百个容器
隔离程度 硬件级强隔离 进程级隔离，性能损耗极低
打包体积 GB 级别（完整系统） MB 级别（仅应用依赖）

Docker C/S架构图

Client：docker 命令行，输入指令发送给守护进程

Daemon (dockerd)：后台服务，管理镜像、容器、网络、存储

Registry：远程镜像仓库（Docker Hub、阿里云镜像仓库）

二、核心概念：镜像、容器、仓库

学习 Docker，必须理解这三个核心概念：

镜像 (Image)：

是什么： 镜像是一个只读的模板，它包含了运行应用程序所需的一切：代码、运行时、库、环境变量和配置文件。

类比： 你可以把镜像想象成一个面向对象编程中的“类”。

**分层特性：**每层只读，可复用，构建时缓存加速

**关键：**镜像不能修改，运行时自动生成一层可读写层

容器 (Container)：

是什么： 容器是镜像的运行实例。镜像是静态的，而容器是动态的。我们对容器的任何修改（如创建、启动、停止、删除）都不会影响到镜像本身。容器删除后，容器内读写层数据默认全部丢失（需数据卷持久化）

类比： 如果镜像是“类”，那么容器就是这个“类”的一个“实例对象”。

仓库 (Repository)：

是什么： 仓库是集中存放镜像文件的地方。

类比： 你可以把它理解成代码界的 GitHub，只不过它存放的是镜像而不是代码。最著名的公共仓库是 Docker Hub。

公共仓库：Docker Hub（官方）、阿里云镜像加速

私有仓库：企业自建 Harbor，存放内部业务镜像

三者关系： 我们从 仓库 pull (拉取) 镜像到本地，然后以这个镜像为模板，run (运行) 起一个或多个容器。

三、什么时候用Docker？

  1. 多人协作开发

    每个人电脑系统、软件版本不一样，有人 Windows、有人 Ubuntu，本地项目环境五花八门，代码拉下来各种依赖报错。统一用 Docker 镜像，所有人环境完全一致。

  2. 本地搭建中间件

    需要临时跑 MySQL、Redis、Nginx、MQ，不想本机安装一堆软件、卸载不干净污染系统，容器用完直接删除，不留残留。

  3. 项目部署上线

    本地能跑，放到云服务器、测试机大概率环境出错；Docker 打包整套环境，服务器只装 Docker，一条命令启动项目。

  4. 多版本软件共存

    比如同时需要 Python3.8、Python3.11，本地安装会冲突，容器分开隔离，互不影响。

  5. CI/CD 自动化流水线

    Git 提交代码后，自动构建 Docker 镜像、自动部署到测试 / 生产服务器。

  6. 临时测试、演示项目

    给别人演示程序，不用对方安装环境，只需要给镜像，一键运行。

不适合：需要独占硬件显卡、深度修改系统内核、桌面 GUI 大型图形程序。

5. Dockerfile 完全指南

Dockerfile 是构建镜像的脚本，每条指令创建一个新的镜像层。

常用指令详解

指令 说明 注意事项
FROM 指定基础镜像 推荐官方镜像，如 ubuntu:22.04，alpine:3.18
RUN 执行命令并提交新层 多条命令用 && 串联减少层数；安装包后清理缓存
COPY 从构建上下文复制文件到镜像 推荐替代 ADD，更透明
ADD 类似 COPY，但支持 URL 和自动解压 tar 谨慎使用，可能导致意外行为
CMD 容器启动时的默认命令 可被 docker run ... 覆盖；使用 exec 形式 ["executable","param1"]
ENTRYPOINT 容器入口点，不易被覆盖 与 CMD 配合可构建“可执行镜像”
ENV 设置环境变量 敏感信息勿用，会被 docker inspect 看到
WORKDIR 设置工作目录 推荐用绝对路径，避免 RUN cd 导致的当前目录混乱
EXPOSE 声明容器监听的端口 仅文档化，实际映射需 -p
VOLUME 创建挂载点 用于数据持久化，但无法指定宿主机路径，运行时用 -v 更好
USER 指定运行用户 安全最佳实践：不要用 root

6. 网络与存储深入

网络模式

  • bridge（默认）：容器连接虚拟网桥 docker0，通过 NAT 与外界通信。
    端口映射 -p 宿主机端口:容器端口 可将服务暴露。
  • host：容器直接使用宿主机网络栈，性能最高，但无隔离，端口冲突风险。
  • none：无网络。
  • 自定义桥接网络：容器间可通过容器名互相访问，因为内置 DNS。

  • 绑定挂载（Bind Mount）：挂载宿主机指定路径。

9. 底层实现原理

Namespace 隔离

Linux Namespace 让容器认为自己是独立的系统。

  • PID namespace：容器内进程 PID 从 1 开始，看不到宿主机进程。
  • NET namespace：拥有自己的网卡、IP、路由表。
  • IPC namespace：隔离信号量、消息队列。
  • MNT namespace：隔离文件系统挂载点。
  • UTS namespace：隔离主机名。
  • USER namespace：隔离用户和组 ID。

Cgroups 资源限制

Control Groups 限制和监控资源使用。

  • CPU：--cpus=2（使用 2 个核心），--cpu-shares 相对权重。
  • 内存：--memory=512m，超过限制会触发 OOM Killer。
  • 块 IO：--blkio-weight。
    可在 /sys/fs/cgroup/ 查看配置。

联合文件系统与 Overlay2

Docker 镜像分层存储依赖 Overlay2 存储驱动。

  • lowerdir：只读镜像层。
  • upperdir：容器可写层。
  • merged：统一视图，包含所有层的叠加。
  • 写时复制：修改文件时，从 lowerdir 拷贝到 upperdir 再修改，确保镜像层不变。

docker image inspect 可查看各层信息。

11. 异常排查与常见问题

容器意外退出

现象：docker ps -a 显示 Exited (1) 或 Exited (137)。

  • 退出码 1：应用自身错误，检查日志 docker logs <container>。
  • 退出码 137：容器被 SIGKILL 杀死，通常因内存 OOM 或 docker stop 超时。
    解决：增加内存限制，或检查应用内存泄漏。

OOM Killed

日志中出现 Killed 且状态码 137。

bash

如果为 true，调高 --memory 限制或优化程序。

网络不通

  • 检查容器是否在同一网络：docker network inspect <network>。
  • 使用自定义网络确保容器名解析。
  • 防火墙规则：sudo iptables -L -n，Docker 会自动添加规则，但可能被其他工具覆盖。

文件权限错误

挂载宿主机目录时，容器内用户 UID 与宿主机文件属主不匹配导致 Permission denied。

  • 运行时指定用户：docker run -u $(id -u):$(id -g) ...
  • 在 Dockerfile 中创建与宿主机相同 UID 的用户。

动态库缺失

docker logs 显示 error while loading shared libraries: libxxx.so.

  • 进入容器检查：ldd /usr/local/bin/echo_server
  • 将缺失的库 COPY 到镜像并 ldconfig。

Core Dump 调试

容器内程序段错误但无 core 文件。

  • 运行容器时允许 core dump 并设置 core 模式：

bash

或在宿主机配置：echo '/tmp/cores/core.%e.%p' | sudo tee /proc/sys/kernel/core_pattern，但注意 Docker 默认会隐藏宿主机的 core_pattern。可挂载 /proc/sys/kernel/core_pattern 只读或使用特权容器。
推荐方案：在容器内启用 core dump 并将 core 文件保存到挂载的卷。

12. 安全最佳实践

  1. 使用非 root 用户：USER 1000 或在 Dockerfile 最后切换。
  2. 最小权限：--cap-drop ALL --cap-add NET_BIND_SERVICE 移除不需要的内核能力。
  3. 只读根文件系统：--read-only，结合 tmpfs 挂载临时目录。
  4. 镜像漏洞扫描：使用 docker scan 或 Trivy。
  5. 不硬编码密钥：用环境变量、Docker secrets（Swarm）或外部密钥管理。
  6. 保持基础镜像更新：定期重建镜像获取安全补丁。
  7. 限制资源：防止 DoS 攻击。

13. 大厂面试官深挖问题集

Q1: Docker 和虚拟机的区别是什么？

答：

  • 虚拟机虚拟化硬件，运行完整 Guest OS，隔离强但资源开销大。
  • Docker 与宿主机共享内核，通过 Namespace 隔离进程、网络等，Cgroups 限制资源，轻量快速，镜像分层存储节省空间。

Q2: 如何优化 Docker 镜像大小？

答：

  • 使用轻量基础镜像（alpine, debian:slim）。
  • 多阶段构建，仅保留运行所需的二进制和库。
  • 合并 RUN 指令，清理缓存（rm -rf /var/lib/apt/lists/*）。
  • 使用 .dockerignore 排除不需要的文件。
  • 避免安装调试工具。

Q3: Overlay2 文件系统的工作原理？

答：
Overlay2 通过多个目录组成联合挂载：lowerdir（只读镜像层）、upperdir（容器可写层）、merged（统一视图）。写时复制：修改文件时，从 lowerdir 复制到 upperdir 再修改。

Q4: 如何保证容器的高可用？

答：

  • 重启策略 --restart=always。
  • 健康检查，自动检测并重启异常容器。
  • 多实例负载均衡（nginx / HAProxy）。
  • 资源限制防止 OOM。
  • 日志集中收集与监控（ELK, Prometheus）。
  • 编排工具（Swarm, K8s）实现自动扩缩容和故障恢复。

Q5: 容器内应用收不到 SIGTERM 信号怎么办？

答：
确保 CMD/ENTRYPOINT 使用 exec 形式（["executable","param1"]），因为 shell 形式（CMD command）不会转发信号给子进程。也可使用 STOPSIGNAL 指定信号。

Q6: 如何排查容器内网络不通？

答：

  • docker network inspect 确认网络配置。
  • docker exec 进入容器 ping 目标，检查 DNS 解析。
  • 检查宿主机 iptables 规则。
  • 使用自定义网络而不是默认 bridge，以利用内置 DNS。

Q7: 你如何实现 C++ 应用的容器化？请描述完整流程。

答：
（根据本文实战部分回答）编写 Dockerfile，使用多阶段构建：第一阶段安装 g++、依赖库，编译源码；第二阶段仅拷贝可执行文件和运行时依赖，设置非 root 用户、健康检查，最后通过 Compose 定义服务并部署。
