分布式理论基石：从小白到理解系统设计的根基

本文是“分布式面试复习骨架”的第一部分详细填充，目标读者是完全零基础的小白。我会用尽可能直白的语言，把抽象的理论讲得足够清晰。读完这篇，你将理解 CAP、BASE、一致性模型和系统模型这些面试高频考点背后的原理，而不仅仅是背诵定义。

0. 为什么我们需要这些理论？

在开始之前，先想象一个最简单的场景：你写了一个单机程序，所有数据都在一台机器的内存或磁盘里，事情很简单——你读到的永远是最新的写入，不会出现一会儿看到数据、一会儿又看不到的怪事。现在，为了应对更大的流量、更高的可用性，你决定把系统拆分成多台机器，每台机器上都有数据副本。这时候，问题就来了：

  • 如果网络出现故障，机器 A 刚刚写入成功，但还没来得及告诉机器 B，此时客户端从 B 读数据，是返回旧值还是拒绝服务？
  • 假如机器 A 和机器 B 都认为自己是“主节点”，同时处理写请求，数据怎么融合？
  • 假设我们用时钟来判断操作的先后，可每台机器的时钟并不完全同步，那“先”和“后”又该如何定义？

这些困惑，正是分布式系统理论要解决的根本问题。分布式系统理论，本质上就是研究“多台机器通过网络通信，面对不确定的延迟和故障，如何协同工作，对外提供一致、可靠的服务”这一课题。

理论基石的第一部分，我们将学习以下四个核心模块：

  1. CAP 定理 —— 分布式系统不可能三角
  2. BASE 理论 —— 最终一致性的哲学
  3. 一致性模型谱系 —— “一致”到底有几层含义
  4. 系统模型与故障假设 —— 研究一切问题的前提设定

下面，我们逐一展开，并确保每一部分都讲透原理。

1. CAP 定理 —— 分布式世界的物理定律

CAP 定理是分布式系统领域最著名的论断，也是面试中几乎必问的题目。它由 Eric Brewer 在 2000 年提出，后来被 Seth Gilbert 和 Nancy Lynch 形式化证明，因此也被称作 Brewer’s CAP Theorem。

CAP 定理的内容：在一个分布式系统中，当设计读写操作时，只能同时满足以下三个特性中的两个：

  • 一致性 (Consistency)
  • 可用性 (Availability)
  • 分区容忍性 (Partition tolerance)

简称 “CAP 三者不可兼得”。很多同学会被这个表述误导，以为我们可以随意选择搭配，比如选 CA 系统。但实际工程中，情况更加微妙。

1.1 三个特性的准确定义

要理解 CAP，必须用精确的语言定义每一个字母，而不是字面意思。

一致性 (Consistency) —— 实际上是“原子一致性”或“线性一致性”

在 CAP 语境下，一致性特指 “每次读操作都能读到最近一次写操作的结果”，就像整个系统只有一个副本一样。更严谨的定义是线性一致性 (Linearizability)：存在一个全局的实时操作顺序，所有节点看到的顺序与此一致，且这个顺序符合物理时间的先后。

举个例子：
客户端 A 执行 set x = 1，写请求完成之后，客户端 B 立即执行 get x。如果系统满足一致性，那么 B 一定读到 1，绝不可能读到旧值 0。即使读请求被路由到了另一个还没有完成同步的副本，也必须阻塞直到同步完成，或者返回错误，总之不能返回旧数据。

可用性 (Availability)

可用性指 “每一个非故障节点，对于收到的请求，必须在有限时间内返回一个非错误的响应”。注意关键词：

  • “非故障节点”：自己已经挂掉的节点不算。
  • “有限时间内”：不能无限等待，必须最终给出结果。
  • “非错误的响应”：不能返回系统异常或超时错误，但允许返回旧数据吗？如果要求严格一致性，那么返回旧数据其实也算是一种“错误”表现（因为一致性被违反）。所以可用性和一致性在这里开始冲突。

在实际产品中，可用性通常体现为：系统能正常响应客户请求，哪怕返回的是旧数据或部分数据。

分区容忍性 (Partition tolerance)

分区容忍性是指 “当网络发生分区（即节点之间的消息可能丢失或延迟，甚至一部分节点和另一部分完全阻断）时，系统仍能继续运作”。

网络分区是分布式系统的常态，而非异常。广域网环境下，交换机故障、光纤被挖断、网络拥堵都可能导致任意两台机器无法通信。如果我们放弃分区容忍性，就等于要求网络绝对可靠——这在实际中几乎不可能，除非你建一个不会出问题的局域网，但即便如此，单机宕机本质上也是一种“网络不可达”的表现。

CAP 定理中，P 并非一个可选项，因为分区必然发生。所以 CAP 讨论的实际上是：当网络分区发生时，剩下的部分（大部分节点所在的区域）是选择牺牲一致性还是牺牲可用性。

1.2 为什么三者不能同时满足？

理解这个问题的关键在于冲突时的抉择。我们用最简单的主备异步复制场景说明：

假设你有一个由节点 A、B 组成的分布式存储，数据有副本。某个时刻，网络分区把 A 和 B 隔离开来。

  • 客户端 1 和节点 A 在同一分区，它能连上 A。
  • 客户端 2 和节点 B 在同一分区，它能连上 B。

现在客户端 1 向 A 写入 x=1，A 成功写入，但无法将此更新同步给 B（因为网络不通）。
随后，客户端 2 向 B 发起读 x 的请求。

系统面临两个选择：

  1. 选择一致性，牺牲可用性：B 由于无法确认自己的数据是否最新，且无法联系 A 同步，于是拒绝客户端的读请求（返回错误）。此时系统可用性丢失，但保证了一致性（没人能读到陈旧数据）。这就是 CP 系统。
  2. 选择可用性，牺牲一致性：B 直接返回自己当前的旧值 x=0，虽然数据不是最新的，但系统在分区的两端都保持可用。这就是 AP 系统。

你不可能让 B 既返回正确的数据（一致性）又不拒绝请求（可用性），因为网络不通，B 根本没有办法知道最新的数据。因此，三者最多满足其二。注意，CA 系统意味着不存在网络分区，这种系统在现实分布式场景下几乎不存在（除非你把整个系统部署在一台不会出现网络故障的机器上，但那就不叫分布式系统了）。所以 CAP 的实际指导意义是：当网络分区发生时，你只能在 CP 和 AP 之间二选一。

1.3 常见的 CP 与 AP 系统举例

  • CP 系统（优先一致性，牺牲部分可用性）：
    • ZooKeeper：当集群发生网络分区，Leader 所在的分区继续服务，但少数派（无 Leader 分区）的所有节点会拒绝请求，直到重新选出 Leader，因此可能短暂不可用。它保证了顺序一致性（稍后详述）。
    • etcd：使用 Raft 共识算法，读请求也需要 Leader 确认，分区时少数派不可用，保证线性一致性读。
    • HBase 强一致性模式：写入必须先写 WAL，并通过共识保证，发生分区时会 fail-fast。
  • AP 系统（优先可用性，接受最终一致）：
    • Eureka（Netflix 服务注册中心）：节点间数据通过异步复制，分区时每个节点可独立提供读写，可能读到过期的服务实例信息，但系统整体可用。
    • Cassandra：使用最终一致性，通过 Quorum 读写配合多副本，无主设计，网络分区两端均可对外服务，后续通过反熵修复不一致。
    • DynamoDB（早期 Dynamo 论文）：永远可写，冲突通过客户端或应用层合并（向量时钟）。

1.4 CAP 定理的常见误区

误区一：“CAP 必须三选二，我设计系统时就固定 CP 或 AP。”
实际上，CAP 特性往往可以细粒度控制。例如，一个分布式数据库可以允许用户对每次查询选择一致性级别（像 Cassandra 的 ONE, QUORUM, ALL）。系统在无网络分区时可以同时满足 C 和 A，只有发生分区时才会触发取舍。

误区二：“CAP 中的 C 就是数据库事务的 ACID 里的 C。”
完全不同。ACID 的 C 是一致性，指事务执行前后数据满足所有约束（如账户余额不能为负），这是应用层的概念；而 CAP 的 C 指分布式数据副本的线性一致性，是一种分布式读写语义。

误区三：“既然网络分区不可避免，CA 系统不存在，那我们就该忘掉 CA。”
CA 系统在单机领域是成立的，例如单机关系型数据库。我们讨论分布式时，默认 P 必须被容忍，因此讨论 CP 与 AP 才有意义。

1.5 CAP 的延伸：PACELC 定理

CAP 只覆盖了分区发生时的取舍，但系统大部分时间可能运行在无分区状态。Daniel Abadi 提出了 PACELC 定理，补充了正常情况下的权衡：

  • if Partition (P): 选择 A 还是 C；
  • else (E): 即使无分区，也要在 Latency (延迟) 和 Consistency (一致性) 之间取舍 (LC)。

典型举例：

  • 分布式数据库：无分区时，为了低延迟读可能读到从库的稍旧数据（牺牲 C 换 L），而非强制读主库。
  • Dynamo 风格系统默认 AP，且在无分区时也是允许低延迟的非严格一致性（即 PACELC 的 PA/EL）。

了解 CAP 和 PACELC，你就能在面试中展示出对“工程权衡”的深刻理解。

2. BASE 理论 —— 最终一致性的哲学

如果说 CAP 定理是“分布式界的相对论”，告诉人们有无法突破的限制；那么 BASE 理论就是“适应这一限制的生存哲学”——它告诉我们，如何设计出既高可用又能跑得快的系统。

BASE 是由 eBay 的架构师 Dan Pritchett 提出的，是对传统关系型数据库 ACID 事务的反思。ACID（原子性、一致性、隔离性、持久性）在单机上完美运作，但在跨网络的分区场景下，强一致性会极大影响可用性和性能。于是 BASE 提倡：

  • Basically Available（基本可用）
  • Soft State（软状态）
  • Eventual Consistency（最终一致性）

2.1 Basically Available（基本可用）

基本可用不是指系统大部分时间可用，而是在系统出现故障时，允许损失部分功能或响应时间，保证核心功能仍然可用。

举例：

  • 电商大促时，流量暴增，系统可以返回一个“服务繁忙，稍后再试”的友好页面，而不是完全崩溃；或者搜索推荐功能降级，只保证下单支付链路畅通。
  • 数据库发生网络分区，可以允许读从库读取可能稍旧的库存数据，而不是直接报错阻断购买流程。

它体现了“有损服务”的思想：宁可少给点、慢一点，也不能让整个系统雪崩。

2.2 Soft State（软状态）

软状态指的是系统中的数据允许存在一个中间状态，且这个中间状态不会影响系统的整体可用性。相对的是“硬状态”，即 ACID 要求的数据时刻处于一致的状态。

比如：订单服务向消息队列发送“订单创建”消息，库存系统消费后扣减库存。在消息未消费之前，订单已创建但库存尚未扣减，这就存在短暂的不一致状态——这个状态就是“软状态”。只要最终扣减成功，业务依然正确。

2.3 Eventual Consistency（最终一致性）

最终一致性是 BASE 理论的核心目标。它意味着：如果系统不再进行新的更新，那么最终所有的读操作都会返回最后一次更新的值。注意前提“不再有新的更新”，在此期间数据副本可能不一致，但系统保证经过一段时间后达到一致。最终一致性不规定时间上限，但实际系统通常会通过协议尽量缩短时间窗口。

最终一致性有很多变种，取决于具体场景，比如：

  • 因果一致性：有因果关系的操作顺序必须被所有节点认可，无因果关系的可以不一致。
  • 读己之写（Read-your-writes）：用户自己总能看到自己提交的更新。
  • 会话一致性：在一个会话内保证单调读。

这些都属于最终一致性的范畴，我们会在第三部分详细展开。

2.4 为什么 BASE 是互联网系统的必然选择？

互联网应用面对的是海量用户和不可靠的网络，不可能保证每个操作的强一致性。ACID 的强事务会导致资源锁定和等待，严重影响吞吐量。所以互联网架构逐渐演变为：“尽可能采用异步解耦，接受数据有短暂窗口的不一致，通过补偿、反查等方式达成最终一致”。这与 BASE 理论完全吻合。

面试时，当被问到“如何处理分布式事务”时，从 ACID 讲到 BASE，再引出具体的柔性事务方案（TCC、SAGA、本地消息表），会非常有层次。

3. 一致性模型谱系 —— 从最强到最弱

很多小白把“一致性”等同于“数据一模一样”，但在分布式语境下，这是一个丰富的谱系。理解不同一致性模型，能够帮助你在设计系统时精确选择你能接受的“不一致程度”，同时这也是面试中证明理论功底的利器。

下面从最强到最弱，逐一剖析。

3.1 线性一致性 (Linearizability) —— 最强

定义：也称为强一致性、原子一致性。它要求：一旦某个读操作读取到了某个值，那么所有后续的读操作（按物理时间）都必须返回那个值或更新的值。也就是说，整个系统表现得就像只有一个副本，所有操作都按某个全局实时的顺序原子执行。

形象的比喻：一个黑板，每个人写上去的东西，其他人立刻看见。任何后看的都不会看到旧内容。

面试关键词：实时顺序、像单机一样、Cap 的 C。

系统举例：etcd 通过 Raft 共识，线性一致性读需要到 Leader 确认；Google Spanner 通过 TrueTime API 实现外部一致性的分布式事务，本质上提供了线性一致性。

3.2 顺序一致性 (Sequential Consistency) —— 强，但允许瞬间的滞后

定义：Lamport 提出，系统所有操作的执行结果，必须像是按某个全局顺序执行的，且每个客户端内部的执行顺序保持不变。但是，不要求该全局顺序符合物理时间的先后。换句话说，如果写操作 A 物理时间上先于写操作 B，但顺序一致性允许系统让 B 的效果先被某些客户端看到，只要所有客户端最终看到的顺序就是那个全局顺序。

关键区别：线性一致性 = 顺序一致性 + 实时约束（操作顺序必须与物理时钟顺序一致）。顺序一致性放松了实时要求，因此可能允许短暂的“非理性”：比如你在 9:00:00 写入了数据，但在 9:00:01 另一个客户端的读可能还是旧值，因为系统认为的全局顺序中那个写被排在了读之后。

系统举例：ZooKeeper 对客户端的操作保证顺序一致性。假设两个客户端分别更新同一个 znode，ZooKeeper 会赋予它们一个顺序，所有客户端将看到同一个历史，但可能一个客户端认为自己先写，却被排到了后面，这是允许的。ZooKeeper 默认不保证线性一致性的读（除非调用 sync）。

3.3 因果一致性 (Causal Consistency) —— 松于顺序一致

定义：如果有因果关联的操作，它们必须按因果顺序被所有节点看到；没有因果关系的并发操作，不同的节点可以有不同的顺序。

“因果”如何定义？基于 Lamport 的 happened-before 关系。如果事件 A 发生在事件 B 之前（可能因为 A 在同一个进程内先于 B，或者 A 是发送消息，B 是接收消息），那么任何节点必须保证看到 A 的影响先于 B。而并发事件（无因果链）的顺序无所谓。

实现工具：向量时钟 (Vector Clock)。每个节点维护一个向量 [node1_counter, node2_counter, ...]，通过向量比较可以判断两个事件是否有因果依赖。

系统举例：Amazon Dynamo 通过向量时钟来检测并发冲突，由客户端解决或将多个版本返回。因果一致性是最终一致性的一种较强形式。

3.4 最终一致性 (Eventual Consistency) —— 最宽松的保证

定义：如果不再有新的更新，那么最终所有副本都会达到一致的状态。这段时间内，不同节点可能返回不同的值。最终一致性不规定顺序，也没有因果保证。

典型变种：

  • 单调读 (Monotonic Reads)：保证同一个客户端不会读到回滚的数据，即每次读到的数据版本不会倒退。
  • 读己之写 (Read Your Writes)：自己写入的数据，一定能被自己后续读到。
  • 会话一致性：在一个会话内提供读己之写和单调读，会话结束则保证弱化。
  • 前缀一致性 (Consistent Prefix)：保证读到的数据版本可以形成一个合法的操作前缀，不会出现无因果的时间倒序（但没有要求因果一致性那么完整）。

系统举例：DNS 系统是典型的最终一致性，某个域名修改 DNS 记录后，各个 DNS 服务器可能数小时甚至数十小时才能同步一致。Cassandra 默认提供最终一致性，但可通过 QUORUM 参数调整一致性级别，结合读写修复机制。

3.5 一致性模型的意义

为什么需要这么多模型？因为强一致性需要高昂的代价。线性一致性通常要求所有操作经过共识或加锁，性能低下，可用性低（如发生分区时不可用）。而很多互联网场景不需要这么强的一致性，例如社交媒体的点赞数，短暂的不一致不影响用户体验。根据业务需求在一致性谱系上选择合适的点，正是分布式系统设计的关键。

面试时，如果你能画出这个谱系，并说出每个模型的特点和代表系统，会让人眼前一亮。

4. 系统模型与故障假设 —— 算法设计的基石

任何分布式算法都建立在一系列假设之上。如果不明确这些假设，我们讨论“算法能否工作”将毫无意义。系统模型就是这些假设的精确表述。

4.1 故障模型 (Failure Model)

节点或通信可能出什么故障？从最轻到最重：

  • Fail-Stop（崩溃停止）：节点一旦崩溃，就完全停止，不再产生任何输出。其他节点可以通过超时检测到它的崩溃。这是最乐观的模型，大部分分布式共识算法（Raft、Paxos）都基于此模型。
  • Fail-Recover（崩溃恢复）：节点可能崩溃并在一段时间后恢复，恢复时丢失内存数据但持久化存储完好。更接近现实。
  • Omission Fault（遗漏故障）：节点可能收到消息但不响应，或者不发送某些消息。可认为是网络与节点的暂时异常。
  • Byzantine Fault（拜占庭故障）：节点可能任意行为，包括发送伪造的消息、做出恶意的或完全不可预测的动作。来源于拜占庭将军问题。解决拜占庭故障的共识协议（如 PBFT）需要更多的节点（通常 n > 3f），且性能较差。在区块链和宇航系统中常见。

在绝大多数企业后端系统中，我们默认使用 Crash-Recovery 或 Fail-Stop 模型，因为机器一般不会故意作恶，但可能崩溃。拜占庭故障常用于开放、无许可的区块链网络。面试时，如果讨论的算法基于 Raft，你应该指出它假设了非拜占庭故障。

4.2 网络模型 (Network Model)

分布式系统节点之间通过网络通信，网络可能发生各种不确定的延迟和消息丢失。根据对时间延迟的假设，分为三类：

  • 同步网络 (Synchronous)：消息延迟有已知上限，节点处理速度有已知上限。在这个模型下可以设计确定性的停止故障检测，FLP 不可能性也不成立。但实际广域网几乎无法提供这种假设。
  • 异步网络 (Asynchronous)：消息延迟无界，节点处理速度无界，没有可靠的超时机制。这是最一般的模型，FLP 不可能性就是在纯异步系统下证明的：没有任何确定性的共识算法能保证安全性和活性。
  • 部分同步网络 (Partially Synchronous)：绝大部分时间网络是同步的（存在未知但有限的消息延迟上限），但偶尔会违反。这是实际系统中最常用的模型，Raft、Paxos 等共识算法都在此模型下保证安全性和最终活性。它们使用超时检测失效，但超时长度是启发式的。

面试时，当被问到“为什么 Leader 选举需要随机超时”，你可以回答：“因为系统假设部分同步，我们无法区分真正的故障和慢节点，随机超时可以降低分裂投票的概率。”

4.3 时间假设

分布式系统经常需要判断事件的先后，于是涉及时间。

  • 物理时钟：每台机器有自己的时钟，通过 NTP 同步，但存在漂移和误差。不能用于精确的全局排序。
  • 逻辑时钟 (Lamport Clock)：只保证 happened-before 事件单调递增，给每个事件一个递增的计数器，但无法区分并发事件。
  • 向量时钟 (Vector Clock)：能检测因果和并发。
  • 混合逻辑时钟 (HLC)：结合物理时钟和逻辑时钟，用于实际系统中生成接近实时的全局顺序，如 CockroachDB。

CAP/一致性模型/共识协议都与时间假设紧密相关。例如，线性一致性要求操作遵循实时顺序，这就依赖于某种物理时钟或全局定序机制。

4.4 FLP 不可能性 —— 不能不知道的理论极限

FLP (Fischer, Lynch, Paterson) 定理：在一个完全异步的系统中，即使只有一个节点可能发生崩溃故障，没有任何确定性的共识算法能够同时保证安全性和活性（可用性）。也就是说，在纯异步网络上，共识问题是不可解的。

该定理的意义：不是共识不可能，而是“我们不能在理论上保证算法一定会在有限时间内结束”。实际上，通过引入部分同步假设、随机化（如随机超时）或者失败检测器，工程系统可以达成共识。Raft 之所以能工作，是因为它假设网络大部分时间是同步的，而且使用了随机超时来打破活锁。

在面试中提到 CAP 时，若能自然引出 FLP 并说出其实践中如何绕过（部分同步），会极大提升你的理论深度。

分布式共识与一致性协议：从 Paxos 到 Raft，再到 ZAB

本文是“分布式面试复习骨架”的第二部分详细填充，面向零基础小白。我会从共识问题的本质出发，逐步深入 Paxos、Raft 和 ZAB 这三种工业界最重要的共识协议，最后给出它们之间的全面对比。读完这篇文章，你将彻底理解分布式系统如何让多台机器在故障面前达成一致。

在上一篇中，我们讨论了 CAP 定理，知道了网络分区时必须在一致性和可用性之间进行取舍。那么，当系统选择了 CP（优先一致性）时，它究竟是怎样在多节点间达成一致的？ 这正是共识协议要解决的问题。

共识问题是分布式系统理论中最经典、最核心的问题之一。通俗地讲，就是让一组机器在某个值（比如数据日志的顺序、谁是主节点）上达成一致，即使其中一些机器可能会崩溃、网络可能会断连。共识协议确保了所有正常节点最终都会做出相同的决定，且决定一旦做出就不会被推翻。

我们将学习三种最具代表性的共识协议族：

  • Paxos：公认的理论鼻祖，但以难以理解和实现著称。
  • Raft：为了可理解性而设计，现已成为业界标准。
  • ZAB：ZooKeeper 使用的原子广播协议，专为协调服务优化。

这三种协议的核心目标一致，但设计哲学和细节各有不同。掌握它们，你将能回答面试中关于“为什么 ZooKeeper 不用 Raft？”“Paxos 和 Raft 有什么根本区别？”等灵魂拷问。

1. 共识问题的形式化定义与挑战

在深入具体协议之前，我们先精确定义共识问题，并了解它为什么难。

一个共识算法通常需要满足以下三个性质（以单值共识为例）：

  1. 终止性 (Termination)：所有正常节点最终都会做出决定（Liveness 活性）。
  2. 协定性 (Agreement)：所有正常节点做出的决定必须相同（Safety 安全）。
  3. 有效性 (Validity)：决定的值必须是某个节点提议的值（不允许凭空捏造）。

此外，在分布式系统中，共识算法还需要容忍节点崩溃、网络延迟和分区。FLP 不可能性已经证明，在纯异步网络中，即使只有一个节点可能崩溃，也不存在确定性的共识算法能同时满足安全性和活性。这一定理为所有共识协议设置了理论天花板：想要达成共识，必须对网络模型做出额外假设。Paxos、Raft 和 ZAB 都基于“部分同步网络”的假设，并采用随机超时等机制绕开 FLP 的活性困境。

2. Paxos 协议 —— 共识算法的理论基石

Paxos 由 Leslie Lamport 在 1990 年代提出，由于其清晰的理论结构和数学证明，被誉为分布式共识的“圣经”。但因为论文使用了虚拟的帕克索斯岛议会作为比喻，导致早期很多人觉得晦涩难懂。实际上，Basic Paxos 的核心流程并不复杂。

2.1 系统模型与角色

Paxos 假设节点可以崩溃、可以重启，但不会发生拜占庭故障（非恶意）。消息可以延迟、重复、丢失，但不会被篡改。

协议中有三种角色：

  • 提议者 (Proposer)：提出值，推动协议。
  • 接受者 (Acceptor)：投票接受提议。
  • 学习者 (Learner)：学习最终决定的值。

一个节点可以身兼多角。通常集群中每个节点都承担 Proposer 和 Acceptor 的角色。

2.2 Basic Paxos 两阶段流程

Basic Paxos 用于就单个值达成一致（即单决议共识）。它分为两个阶段，每个阶段都有请求和回复。

阶段一：Prepare 准备阶段

目的：获得向 Acceptor 提出提案的权利，并了解可能已经存在的已被部分接受的值。

  1. Proposer 选定一个全局唯一且单调递增的提案编号 n（通常为时间戳加节点 ID），然后向所有 Acceptor 发送 Prepare(n) 请求。
  2. Acceptor 收到 Prepare(n) 后，检查自己是否曾经承诺过不接受编号小于 n 的 Prepare 请求（也就是它可能已经响应过一个编号更高的 Prepare）。如果没有，则做出承诺：
    • 不再接受任何编号小于 n 的 Prepare 或 Accept 请求。
    • 如果它之前已经接受过某个提案 (n', v')，就将它返回给 Proposer；否则返回空。
      Acceptor 回复 Promise(n, n_prev, v_prev)，其中 n_prev, v_prev 是它接受过的最高编号提案及其值。

当一个 Proposer 收到多数派 Acceptor 的 Promise 回复时，阶段一结束。多数派是关键，它保证了后续任何阶段二如果也有多数派接受，那么它们必有交集。

阶段二：Accept 接受阶段

目的：使多数派接受一个值，达成决议。

  1. Proposer 从收到的 Promise 回复中，选择一个值作为本次提案的值 v：
    • 如果所有回复都没有附带任何已接受的值，则可以任意提议一个新值。
    • 如果有任何一个回复附带了 (n_prev, v_prev)，则必须选择其中 n_prev 最大的那个对应的 v_prev 作为本次提案的值。这个规则至关重要，它保证了已经达成或可能达成的值不会被覆盖。
  2. Proposer 向所有 Acceptor 发送 Accept(n, v) 请求。
  3. Acceptor 收到 Accept(n, v) 后，检查自己是否还没有承诺过编号大于 n 的 Prepare（即它可能已经响应了更高编号的 Prepare 而背弃了之前的承诺）。如果没有，则接受该提案，并回复 Accepted(n, v)；否则拒绝。

一旦 Proposer 收到多数派 Acceptor 的 Accepted 回复，该值就被选定 (Chosen)。此时，学习者就可以学习到这个值。

2.3 Paxos 的关键性质：安全性保证

Basic Paxos 通过上述流程保证了：

  • 协定性：一旦某个值被多数派接受，任何后续的提案如果成功，其值一定与该值相同。这是因为后续 Proposer 在阶段一必然会从某个接受过该值的 Acceptor 那里获知该值，并在阶段二提议它。
  • 有效性：被选定的值必然来自某个 Proposer 的提议。
  • 活性方面，Basic Paxos 可能会因为多个 Proposer 互相抢占而陷入活锁：例如 Proposer A 发出 Prepare(n1) 获取了多数派承诺，随后 Proposer B 发出更高的 Prepare(n2) 又让 Acceptor 承诺更高编号，导致 A 的 Accept 请求被拒绝。A 再用 n3 > n2 重试，如此反复，系统可能无法达成决议。工程上通过引入领导者 (Leader) 来避免活锁，即一次只有一个 Proposer 可以发起提案，这就是 Multi-Paxos 的起点。

2.4 从 Basic 到 Multi-Paxos

实际系统不可能只对一个值达成共识，而是需要对一系列命令达成一致（比如数据库的复制日志）。Multi-Paxos 将 Paxos 实例串联起来，为日志中的每一个槽位运行一次 Basic Paxos。

Multi-Paxos 的优化：

  1. 选举一个稳定的 Leader：由它充当所有 Paxos 实例的 Proposer，极大减少了冲突和两阶段开销。
  2. 省略 Prepare 阶段：当 Leader 稳定且任期未变时，对于后续的提案，可以直接从阶段二开始（Accept），因为该 Leader 已经通过一次成功的 Prepare 获得了多数派的承诺。只有当 Leader 失效或发生变更时，新的 Leader 才需要重新执行 Prepare 阶段（对应 Leader 选举过程）。
  3. 日志结构：每个节点维护一个日志，Leader 按顺序为每个日志项运行一次 Paxos 实例，记录状态机命令。

Multi-Paxos 虽然思想清晰，但缺乏工程细节标准，各家实现差异很大，比如 Google Chubby、Spanner 都实现了自己的 Multi-Paxos 变种。这也是后来 Raft 出现的背景。

3. Raft 协议 —— 为可理解性而生

Raft 是 Diego Ongaro 和 John Ousterhout 在 2013 年提出的共识算法，其首要设计目标就是可理解性。它把共识问题分解为三个相对独立的子问题：领导者选举、日志复制、安全，并且采用了强领导者模型，所有日志流都从 Leader 流向 Follower。Raft 容易理解、容易实现，在业界被广泛采用，如 etcd、Consul、TiKV 等。

3.1 Raft 基础概念

  • 节点状态：Leader（领导者）、Follower（跟随者）、Candidate（候选人）。
  • 任期 (Term)：逻辑时钟，用连续整数表示。每个 Term 以一次选举开始，可能选出 Leader，也可能选举失败。如果一个节点发现自己的 Term 小于别人的，则立即更新并转为 Follower。Term 是 Raft 保证时序和安全性的核心。
  • 心跳：Leader 定期向所有 Follower 发送心跳（空的 AppendEntries 请求）以维持权威，抑制选举。
  • 超时机制：Follower 在选举超时时间内未收到 Leader 心跳，就认为自己可以成为 Candidate 发起选举。候选人在候选超时时间内未获得多数票或发现新 Leader，则结束选举。超时时间采用随机值，避免选票瓜分。

3.2 子问题一：领导者选举

Raft 使用心跳触发选举。初始时所有节点都是 Follower，并且有一个随机选举超时时间（如 150-300ms）。一旦 Follower 超时，它做以下动作：

  1. 将自身状态变为 Candidate。
  2. 将当前 Term 加 1，然后给自己投一票，再向所有其他节点发送 RequestVote RPC，包含自己的 Term 和最后一条日志的索引和 Term。
  3. 结果有三种可能：
    • 赢得选举：在同一个 Term 内获得了多数票，则成为 Leader，立即向所有节点发送心跳，确立统治。
    • 收到其他 Leader 的心跳：如果该 Leader 的 Term >= 自己的 Term，则认可对方，自己退回 Follower。如果对方 Term 较小，则拒绝并继续选举。
    • 选举超时 (Split Vote)：多个 Candidate 瓜分选票，没有人获得多数票，当前 Term 选举失败。Candidate 会等待随机超时后再发起新一轮选举（Term 再增加）。

随机超时的重要性：它避免了多个 Candidate 几乎同时超时发起选举导致的无限平局。通常先超时的节点更容易成为 Leader。

3.3 子问题二：日志复制

一旦 Leader 产生，它负责接收客户端请求，并将命令作为日志项复制到所有节点。

日志结构：每条日志项包含 (Term, Index, Command)。Leader 为每个 Follower 维护两个关键索引：

  • nextIndex：下次要发给该 Follower 的日志起始索引，初始为 Leader 的最后一条日志索引 + 1。
  • matchIndex：已知的已在该 Follower 上成功复制的最高日志索引，初始为 0。

复制流程：

  1. Leader 收到客户端命令，将命令追加到本地日志。
  2. Leader 并行向所有 Follower 发送 AppendEntries RPC，其中携带从 nextIndex 开始的新日志项，以及上一条日志的 (prevLogIndex, prevLogTerm) 用于一致性检查。
  3. Follower 收到 AppendEntries 后，进行一致性检查：如果自己在 prevLogIndex 处的日志项的 Term 与 prevLogTerm 相等，则认为日志匹配，可以追加新日志；否则拒绝，返回失败。
  4. 如果一致性检查失败，Leader 会递减 nextIndex 并重试，直到找到匹配点。这种回退机制能快速同步不一致的日志。
  5. 当一条日志项被复制到多数派节点后，Leader 就可以提交 (commit) 这条日志。提交意味着该日志对应的命令已经可以安全应用到状态机，并且将来所有 Leader 都会保证包含这条日志。
  6. Leader 在后续的 AppendEntries 中携带已提交的日志索引 (leaderCommit)，Follower 据此将自己日志中的对应项提交并应用到状态机。

日志的最终一致性：Raft 保证所有节点的日志最终都会与 Leader 一致，且日志提交是持久化的。Leader 绝不删除或覆盖自己的日志，只会通过 AppendEntries 让 Follower 与自己一致。

3.4 子问题三：安全机制

日志复制如果缺乏安全约束，可能导致已被提交的日志在新 Leader 下被覆盖。Raft 通过以下两条关键规则保证领导者完全性 (Leader Completeness)：一旦一条日志在某个 Term 被提交，那么未来所有 Term 的 Leader 的日志中一定也包含这条日志。

3.4.1 选举限制

在 RequestVote RPC 中，Candidate 必须携带自己最后一条日志的 (lastLogIndex, lastLogTerm)。收到投票请求的节点，只有当 Candidate 的日志至少和自己的一样新时，才会投票给它。判断依据：如果 Candidate 的 lastLogTerm 大于自己的，则它的日志更新；若 Term 相同，则比较 lastLogIndex，更大的更新。这个限制保证新选出的 Leader 一定包含了所有已提交的日志项。因为要赢得多数票，它的日志必须跟大多数节点一样新，而已提交的日志恰好位于多数节点上，所以新 Leader 必定拥有那些日志。

3.4.2 提交前一条日志必须属于当前 Term

这是 Raft 一个非常精妙但容易被忽视的细节。Raft 规定：Leader 不能仅仅因为一条之前 Term 的日志被复制到多数派就认为可以提交它，而必须是通过提交一条当前任期的日志，间接地把之前未提交的日志一起提交。 也就是说，Leader 只能提交自己 Term 内的日志项；一旦一条当前 Term 的日志被提交，那么所有之前未提交的日志（由于日志的连续性）也自动被提交。

为什么需要这个限制？考虑一种情景：Leader 在 Term 2 复制了一条日志到多数派，但还没来得及提交就崩溃了；新 Leader 在 Term 3 产生，它并不知道那条日志是否真的已被原来“多数派”确认（因为那个多数派可能已经改变），如果没有这条限制，新 Leader 可能会错误地认为那条日志已提交，从而导致覆盖。通过限制 Leader 只能提交自己 Term 的日志，就避免了这种因前任 Leader 遗留而导致的不确定性。

具体运作：当前 Leader 将自己的日志项 entry@Term_current 复制到多数派后，更新 commitIndex 为这条日志的索引，同时所有之前的未提交日志也一并提交。在之前的 AppendEntries 中，Leader 都会将 leaderCommit 告知 Follower，Follower 据此更新提交。

示例：

  • 时间点1：S1 是 Term 2 的 Leader，将日志条目 (term2, index2) 复制到了 S2 和 S3（多数派），但还没来得及把 commitIndex 更新到 2，S1 崩溃。
  • 时间点2：S5 发起 Term 3 选举并成为新 Leader（S5 可能也拥有 index2 的日志，但未必）。此时，S5 不能因为看到 (term2, index2) 已经在旧多数派上就直接提交它，因为新多数派可能已经变了。S5 会正常进行日志复制，假设它产生一条自己的日志 (term3, index3)。当 (term3, index3) 复制到多数派并提交时，index2 才会随着一起被提交。
  • 这样，即使旧 Leader 的日志未及时提交，也不会造成不一致，因为新 Leader 保证了提交的连续性。

这个机制保证了提交的安全性，是 Raft 与一些 Multi-Paxos 实现的重要区别之一。

3.5 成员变更

集群节点的加入和退出是运维常态，过程必须安全，不能让同一个 Term 内出现两个 Leader。Raft 最初的论文提出了联合共识 (Joint Consensus) 方法，但实现复杂。后来 Ongaro 又提出了更简单的单节点变更方法，并被广泛采用。

单节点变更：每次只向集群中增加或移除一个节点，逐步调整。Raft 的日志机制可以安全地处理这个操作。当需要变更时，Leader 将配置作为特殊的日志条目复制到集群，一旦该配置日志被提交，新旧配置的过渡就完成了。由于一次只变更一个节点，新旧配置的多数派必然有重叠，避免了同一 Term 产生两个 Leader 的可能。etcd 等系统默认使用单节点变更。

3.6 日志压缩与快照

日志会无限增长，Raft 引入了快照 (Snapshot) 机制来压缩日志。节点可以独立地对状态机做快照，然后截断快照之前的日志。Leader 如果发现 Follower 落后太多，可以直接发送快照给 Follower（InstallSnapshot RPC），大幅加速追赶。快照是 Raft 实现中必须处理的部分，但核心共识逻辑不依赖于此。

4. ZAB 协议 —— ZooKeeper 的原子广播

ZAB (ZooKeeper Atomic Broadcast) 是 Apache ZooKeeper 内部使用的共识和广播协议。它并非直接复制 Paxos 或 Raft，而是专门为 ZooKeeper 的协调服务设计，强调高吞吐的顺序一致性和快速故障恢复。

4.1 ZAB 的两种模式

ZAB 协议将工作分为两种模式，不断交替：

  • 崩溃恢复 (Crash Recovery)：当集群刚启动或 Leader 失效时，进入该模式，选举出新的 Leader，并使各节点状态同步。
  • 消息广播 (Message Broadcast)：正常模式，Leader 接收请求，将事务提议广播给 Follower，遵循类似两阶段提交的流程，但确保顺序。

4.2 ZAB 的核心概念

  • 事务标识 Zxid：ZooKeeper 通过 Zxid（64 位数字，高 32 位为 epoch，低 32 位为事务计数器）来唯一标识每个更新操作。epoch 即 Leader 任期，每发生一次 Leader 选举，epoch 加 1。
  • 提议 (Proposal)：Leader 将更新封装为提议，发给所有 Follower。
  • 确认 (ACK)：Follower 收到提议后写入事务日志（持久化），并回复 ACK。一旦 Leader 收到多数派 ACK，就会发送 Commit 消息，通知 Follower 提交并应用到内存数据中。
  • 广播的顺序性保证：Leader 保证提议按 Zxid 顺序广播和提交，且前一个事务的提交不会影响后续事务的处理，可形成管道。

4.3 崩溃恢复与 Leader 选举

崩溃恢复阶段主要完成两件事：选出一个拥有最高 Zxid 的节点作为新 Leader，以及确保在新 Leader 开始广播前，所有节点同步到最新状态。

Leader 选举：ZAB 的选举算法与 Raft 思想类似：每个节点投票给拥有最大 Zxid 的节点，如果 Zxid 相同则选 Server id 最大的。一旦某节点获得多数票，即成为新 Leader。Zxid 最大意味着它的日志可能最新，保障了已提交事务的安全。

同步阶段：

  1. 新 Leader 会把自己的事务日志作为基准。
  2. 其他 Follower 与 Leader 通信，Leader 判断每个 Follower 的日志状态，将缺失的提议和提交信息发送给它们。
  3. 当所有 Follower 同步完毕，或者仅多数派同步完毕（根据配置），新 Leader 才进入消息广播模式。这个过程称为 Synchronization。

4.4 广播阶段的事务流程

在正常消息广播模式下，ZAB 处理一次写入的过程类似于 2PC，但更强调顺序：

  1. Leader 接收写请求，生成提议，赋予单调递增的 Zxid。
  2. Leader 将提议发给所有 Follower。
  3. Follower 收到提议，将提议写入事务日志后，回复 ACK。
  4. Leader 收到多数派 ACK 后，发送 Commit 消息。
  5. Follower 收到 Commit 后，将更新应用到内存数据库。
    同时，Leader 也会应用更新。所有更新按照 Zxid 顺序执行，保证了客户端的操作按顺序被处理，从而提供顺序一致性。

注意：ZAB 不像 Raft 那样要求日志严格匹配，而是更侧重于最终 Leader 的日志成为权威。同步阶段会截断不一致的部分。

4.5 ZAB 与 Raft 的对比

两者都是强领导者模型，都有任期的概念，都有选举和日志同步。但细节差异明显：

  • 提交方式：Raft 的日志提交是连续的，依赖于领导者检查；ZAB 通过显式的 Commit 消息提交。
  • 日志一致性：Raft 强制 Follower 日志必须精确匹配 Leader，通过回退匹配实现；ZAB 在恢复时直接以 Leader 日志为准，截断 Follower 多余的日志，更简单粗暴。
  • 选举依据：Raft 比较最后一条日志的 Term 和 Index；ZAB 比较最大 Zxid，而 Zxid 是 epoch + 计数器，实际上包含了日志的新旧信息。
  • 广播性能：ZAB 的 Commit 消息独立，可以流水线，在处理大量更新时吞吐较高；Raft 通过 AppendEntries 批量发送和提交，两者各有优势。

5. Paxos vs Raft vs ZAB 全面对比

现在我们已经了解了三个协议的核心机制，下面从多个维度进行横向对比，这也是面试中的高频问题。

5.1 设计目标与可理解性

  • Paxos：学术经典，设计简洁但细节抽象，缺少标准工程实现。Lamport 本人也承认很多人难以理解。Multi-Paxos 的实现各家自行演绎。
  • Raft：专为可理解性设计，把问题分解为独立的子模块，提供了清晰的伪代码和边界条件，论文本身甚至包括大量实现指南。使得工程实现非常一致，如 etcd, Consul 等。
  • ZAB：为 ZooKeeper 场景定制，相对于 Paxos 更工程化，但早期没有独立发表的严格形式化描述，理解门槛中等，但不如 Raft 普及。

5.2 领导者角色与选举

  • Paxos：Basic Paxos 没有固定领导者，Multi-Paxos 引入领导者提升性能。选举过程与 Prepare 阶段结合。
  • Raft：强领导者，选举过程独立且简单：随机超时 + 投票请求。Leader 一旦选出，所有日志都由 Leader 决定。
  • ZAB：也是强领导者，选举依赖于 Zxid（最大日志）。选举和新 Leader 同步是两个明确步骤。

5.3 日志复制与提交

  • Paxos：每个日志槽位独立运行 Paxos 实例，理论上允许并发处理，但工程上常常顺序进行。
  • Raft：日志由 Leader 严格有序复制，提交必须满足 “当前 Term 的日志提交才允许间接提交旧日志” 的安全规则，保证了提交的确定性。通过回退 nextIndex 强制匹配。
  • ZAB：通过显式两阶段广播，Leader 收到多数派 ACK 后即发送 Commit，可以流水线处理事务。恢复时 Leader 日志覆盖 Follower。

5.4 成员变更

  • Paxos：没有标准机制，通常通过特殊的 Paxos 实例来传递配置。
  • Raft：提出联合共识和单节点变更，工程上单节点变更简单且安全，应用广泛。
  • ZAB：ZooKeeper 的配置是静态的（可动态修改配置文件但需要重启，新版本支持动态重配，基于 Zab 协议扩展）。

5.5 对一致性的保证

  • Paxos：实现正确时可保证线性一致性（取决于实现）。
  • Raft：保证线性一致性读写（若走 Leader 读确认）。
  • ZAB：保证顺序一致性（客户端看到的顺序符合提交顺序），默认不提供线性一致性读，除非调用 sync。这是因为读可以直接在 Follower 上处理，可能读到旧数据。

5.6 实际应用与生态

  • Paxos：Google Chubby（基于 Paxos），OceanBase 日志流，还有一些自研数据库。
  • Raft：etcd, Consul, TiKV, CockroachDB, Kafka (KRaft) 等，生态最繁荣。
  • ZAB：ZooKeeper 独占，但 ZooKeeper 应用广泛，许多分布式系统依赖它。
